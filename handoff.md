## 1. Project in one paragraph

INNOFEST "Battle It Out" is a Battlecode-2026-style programming competition. Participants submit **Python entry `bot.py`, alone or in a flat-module bundle with curated dependencies (CN-028)**, which plays automatically in the **existing Battlecode 2026 engine** (no replacement engine). The platform covers invitation-based registration, bot submissions, single-elimination brackets, tie-breaks, replays, notifications, audit, and retention. **Order of work: scaffold + Python 3.13 first → bot execution + match automation second → backend → website/landing page last.** CN-028 subsequently authorizes local landing/feature-console work; the execution exit gates still remain open.

## 4. Document digest (all in `docs/`; scaffold README is in `backend/battlecode26-scaffold/`)

### PRD.md — product requirements (v1.0, 2026-11-04)
- Goals: BIO-G01 reproducible scaffold on Python 3.13; G02 safe deterministic bot execution (bot failure ≠ platform failure); G03 automated match lifecycle (advance, tie-break maps, final coin flip); G04 controlled tournament/registration/submission mgmt; G05 visible, auditable outcomes/notifications.
- Personas: Participant (own team only), Organizer (assigned tournaments only; may view/download source, may NOT alter submissions/locked identity/codes), Admin (global; sole authority for code revoke/replace, restore team, permanent tournament delete, emergency override).
- Priorities: **P0** repo audit, Py3.13 scaffold, run single `bot.py`, validate, isolated execution w/ global limits, failure classification, sequential matches/bracket/tie-breaks/coin flip, replay lifecycle, retry policy, prove engine before website. **P1** auth/roles, tournament lifecycle, roster/codes, submissions, audit, notifications, dashboards, deletion lifecycle. **P2** landing page, live viewing, extra languages/multi-file, analytics, disputes.
- Rules: Organizer-created tournaments need Admin approval (reject needs reason; resubmit allowed); registration & submission deadlines independent; Admin may extend (even after expiry); post-deadline edits need extension or emergency override (reason + notify). Invitation = official roster email + single-use code; invalid attempts don't consume code; unused codes expire at close/extension; registration locks email/team/member#/role. Submissions: only `bot.py`, latest valid becomes active, invalid replacement keeps previous active, immutable versions, match stores exact version. Matches: sequential, Organizer starts each round, single-elimination, random pairing, automatic byes (humans before house bots), house bots can't advance/win; normal tie → 1 tie-break map, final tie → 3 maps sequentially, then 50/50 coin flip (no rerolls, logged, displayed); qualification-cutoff tie → automatic random draw. Bot crash/timeout/instruction-limit = auto loss, no rematch. Platform failure → restart same map + same bot versions, **new seed**, retry up to 10 then alert Admin. Replays kept until archive, then deleted for everyone; results/brackets/history remain. Notifications: dashboard mandatory, email optional. Audit logs immutable, permanent, scope-filtered. Deletion: account deletion queued while team competing (cancelable), participant removed entirely from historical rosters (no placeholder), captaincy transfers; team delete only after archive (Admin/Organizer; Admin restores); only Admin permanently deletes tournaments (audit survives).
- NFRs: isolation (P0), global fixed benchmarked limits (don't invent numbers), pinned reproducible runtime, exact-version match records, server-side authz everywhere, append-only audit, private submission files, backups/recovery, secret-free logs, load targets via testing.
- Proposed (NOT approved) stack: React+TS, Django+DRF, PostgreSQL, Celery+Redis, isolated container workers, S3-compatible private storage, polling first, containerized behind reverse proxy.
- Roadmap: EPIC-00 Discovery → 01 Scaffold modernization → 02 Bot runner/sandbox → 03 Match/tournament automation → 04 Backend → 05 Registration/submissions → 06 Tournament ops → 07 Website → 08 QA/pilot/launch. Phase 0–3 task breakdown is in PRD §10.

### Additional findings (2026-11-24, from reading code and running commands)
- **Version "drift" is not drift (corrected 2026-11-24):** `engine_version.txt` 1.2.6 is the Java engine; the official 1.2.6 Python release artifact contains package `battlecode26` 1.2.2 (`.temp/battlecode.tar.gz` is byte-identical, SHA-256 `bf52c038…8b03f9`). Server also reports client 1.0.7 (local 1.0.6) and a private `1.2.7.private2`. `run.py` therefore reinstalls the package on every Python run (1.2.2 ≠ 1.2.6). System `python3` is 3.14.10 and `run.py` rejects it.
- **Python-bot match via Gradle — causes found (2026-11-24):** (1) `build.gradle` runs `python3` from `PATH` (system 3.14, no package) → `No module named battlecode26`; a running Gradle daemon keeps its old `PATH`, use `--no-daemon`. (2) With the venv on `PATH`, `runPyLocal --new-process` deadlocks on Linux: the spawned runner keeps Gradle's pipe open while waiting for the Java server that Gradle starts only after it. **Workaround verified:** start `.venv/bin/python -m battlecode26 …` in the background (output redirected), then `./gradlew runJavaLocal --no-daemon --offline -PlanguageA=python …`. Full Python-vs-Python control match completed: A wins round 1290, 706 s, 64 KB replay, exit 0 (used a `TCP_NODELAY` wrapper in the scratchpad, not in the repo). **Slow:** ~1.6–1.8 rounds/s, runner ~0% CPU, latency-bound; neither Python client nor Java `CrossPlay` sets `TCP_NODELAY`, two writes per message; wrapper gave ~2x; rest unexplained. Java vs Java: ~2 s.
- **Import allowlist:** the engine's Python runner lets a bot import only its own modules plus `random`, `math`, `enum`, `battlecode26`; PRD says "standard library and preinstalled libraries". Needs a decision (bot contract, BIO-201).
- **Isolation (updated 2026-11-24, BIO-203/204, CN-005):** the engine itself is language-level only and runs both teams' robots as threads of ONE runner process behind ONE TCP connection (main thread waits per turn with no timeout; bytecode counter charges game calls only). `backend/match_runner` now runs **one sandboxed process per team** (bubblewrap: no network, ro root, only own bot folder, seccomp denylist, optional cgroups) behind a host-side `Router`, with a wall-clock/memory guard and classification; tested with hostile bots (`docs/TECHNICAL_DOCUMENTATION.md` §3.6). Remaining: no independent security review, interim (not benchmark-approved) limits, engine tie-break seed not controllable.
- **Weak validation:** `run.py verify` only checks `bot.py` exists and contains the text `def turn():`; the only Java test is `1 + 1`; there are no Python tests.
- **License (decided 2026-11-24, CN-003):** project is **AGPL-3.0-only**, same as the vendored scaffold. Battlecode is mixed: scaffold AGPL-3.0, Python package MIT, **Java engine declares no license** (open: ask the Battlecode team). See `docs/LICENSING.md`, `THIRD_PARTY_NOTICES.md`. No legal analysis beyond reading the sources.
- **Gap in API contract:** the Admin navigation lists user/role/organizer assignment, but `API_CONTRACT.md` has no endpoints for it.
