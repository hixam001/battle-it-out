## CN-001 — Python runtime: latest stable CPython (2026-11-24)

- **Owner instruction:** the platform must run on the latest Python version.
- **Replaces:** the "Python 3.13" target (PRD, SRD-003, TEST_PLAN TC-01, APP_FLOW FLOW-01). 3.13 stays in the tested matrix, so every statement of the form "Python 3.13 compatibility is verified" can still be satisfied.
- **What "latest" meant on 2026-11-24:** `uv python list` offered 3.15.2 as the newest stable release (3.16.0a2 is an alpha and was not used). Primary runtime: **3.15.2**. Also tested: 3.14.10, 3.13.18, 3.12.15.
- **Evidence:** `docs/TECHNICAL_DOCUMENTATION.md` section 3.5 (test matrix, 2026-11-24, Linux x86_64 only).
- **Caveat that matters:** the official engine package declares `Requires-Python >=3.12,<3.13` and its own entry point rejects every Python except 3.12. The project runs it on newer versions through its own entry point (`backend/match_runner/runner_entry.py`), without modifying the package. The engine authors do not support this; compatibility is only what our tests show. Re-run the matrix whenever the engine package or the Python version changes.
- **Still open:** DEC-03 (exact patch version and OS matrix) needs the owner's confirmation of 3.15.2 and of Linux x86_64 as the only tested platform.

## CN-005 — Bot execution safety: decisions taken by the engineer under owner delegation (2026-11-24)

- **Owner instruction:** "handle all of this according to yourself" (the open points after the first sandbox version). These are reversible engineering decisions, not benchmark results; the owner can overrule any of them.
- **D1. Numeric limits (DEC-04): an interim profile is in force.** `backend/match_runner/limits.provisional.json`: turn 1.0 s, start-up 2.0 s, resident memory 512 MiB per team process, address space 4096 MiB, CPU 900 s, 256 open files, 16 MiB output, 512 tasks. They are generous multiples of three small bots (longest turn 19 ms, 22 MiB). They are **not benchmark-approved**: the PRD wants benchmarked values, so re-benchmark with realistic bots before a tournament. The file says so inside itself.
- **D2. An uncaught exception in one robot does not forfeit the match.** Engine behaviour is kept: that robot dies, the team plays on. The guard counts exceptions per team in the match record (`usage.teams.X.exceptions`) so the policy can be tightened later without re-running matches. Wall-clock, start-up, memory and process-limit breaches are forfeits. (TEST_PLAN TC-04's "bot crash" is read as a crash of the bot process, not of one robot.)
- **D3. Isolation runtime: bubblewrap + seccomp + cgroups, one process per team.** No container image yet; a container (DEC-11) should wrap the worker, not replace these layers. Each team's runner has its own sandbox; a host-side router joins both to the engine server. Linux x86_64 with unprivileged user namespaces only.
- **D4. Behaviour that differs from the official runner, accepted:** with one process per team, bots no longer share Python module state or the global `random` stream (the official runner puts both teams in one process, so a bot that calls `random.seed()` changes the other team's random numbers). Replays of seeded bots therefore differ from earlier runs of this project.
- **Still open (cannot be decided from here):** the engine's tie-break ("coin flip") is not seeded from anything we control (no seed property was found among the server's `bc.*` settings), so two identical runs can have different winners; TC-04's "retry with a new random seed" needs an engine-side seed. Also: approval of the benchmark-based numbers, the upload size cap.


## CN-006 — Failure classification: who loses when a bot's process dies (2026-11-24)

- **Task:** BIO-205 (classify bot/platform failure). Engineer's decision under the owner's earlier delegation ("handle it yourself", see CN-005); reversible, not an owner ruling.
- **Gap closed:** before this, only a recorded limit breach counted as a bot failure. A bot that crashed its own process (`os._exit`, a segfault, a kill by the operating system, leaving mid-game) was reported as `platform_failure`, which the retry policy would replay up to 10 times.
- **Rule:** if the match did not finish and no limit breach was recorded, whichever side **hung up the engine connection first** decides. That fact comes from the host-side router, which sits outside every sandbox; the runner's own log is not used, because bot code runs inside that process and can print anything.
  - a team's runner ended it first -> `bot_crash`, that team loses (forfeit), no rematch;
  - the engine server ended it first -> `platform_failure` (no loser, no winner);
  - a runner never connected -> `platform_failure` (the platform failed to start it);
  - no clue, or the whole-match timeout -> `platform_failure`.
  Every result also carries `outcome` = `completed | bot_failure | platform_failure`, the three values of the worker contract (API_CONTRACT §8), and for crashes the `evidence` (which leg closed first, exit status, signal name).
- **Trade-off, chosen on purpose:** a crash of the engine's own Python code inside a team's runner cannot be told apart from a bot crashing itself, because they are the same process. Such a crash is charged to that team. The opposite choice would let a losing bot force replays by crashing itself. `evidence` is kept so an Admin can review a suspicious case; a dispute workflow is deferred in the PRD.
- **Other limit:** an operator or the host killing a runner process from outside (for example the kernel's out-of-memory killer outside our cgroup) is also charged to that team, since the router only sees the connection close.
- **Replaces:** nothing in the PRD; it implements PRD "Bot crash/timeout/instruction-limit = auto loss, no rematch" for crashes and keeps "platform failure -> same map and versions, new seed, up to 10 retries".
- **Still open:** TC-04's "retry with a new seed" (the engine tie-break seed is not controllable), the retry loop itself (BIO-306), structured logs (BIO-206).

## CN-007 — Log integrity fix and structured match logs (2026-11-24)

- **Task:** BIO-206 (structured logs). Engineer's decisions under the owner's delegation (see CN-005); reversible, not owner rulings.
- **Defect found and fixed first (my own earlier work):** the launcher read the winner, the reason and the server errors from the engine's console log with unanchored patterns, taking the first match. A bot can write anything into that log through `log(...)`, including line breaks, because the Java server prints the text unescaped. Reproduced on 2026-11-24: a bot that logged `"\n[server]   <its name> (A) wins (round 2)\n[server] Reason: forged"` was reported as the winner with a forged reason; a bot that logged a `[server:error]` line made its own match a `platform_failure`, which the retry policy would replay (so a losing bot could dodge a loss). Neither needed to break out of the sandbox.
- **Fix, two layers:** (1) the router now parses and rebuilds every frame a runner sends (`sandbox.py` `canonical_runner_frame`): a frame must be JSON `null` or `{method: int, params: list}`, anything else ends that runner's connection (charged to that team, like any early hang-up, CN-006); every line break kind in any text becomes a newline plus `  | `, other control characters (including ESC) are dropped, so no bot-controlled line can start with `[server`, `[A: #...` or `BIO-GUARD`. (2) The launcher's parsers are anchored to the start of a line and take the **last** match. The router sits outside every sandbox, so a bot cannot bypass it.
- **Behaviour changes:** runner frames reach the engine as canonical JSON (same content, different bytes; extra keys dropped; duplicate keys collapsed); multi-line bot output appears in the server log with `  | ` before each continuation line; a bot that sends a malformed frame forfeits. `router.text_rewrites` counts rewritten strings per team (a traceback is also multi-line, so a non-zero count is not by itself suspicious).
- **Structured log (new):** every `run` writes `match-<stamp>.events.jsonl` (schema 1) and returns `structured_log` (path, event count, SHA-256). Events carry `trace_id`, `match_id`, `attempt` and a **visibility**: `all`, `team:A`, `team:B` or `staff`. Format and contents: `docs/TECHNICAL_DOCUMENTATION.md` section 3.7.
- **Default for "who may read what"** (API_CONTRACT section 9 item 6 was open): a participant sees `all` plus their own team; an Organizer sees `all` plus both teams; only an Admin sees `staff` (platform diagnostics: exit statuses, router evidence, engine lines). `match_log.view()` is the single place this is decided. Changing it means changing that function and the tests.
- **Redaction** is best effort (host paths, home directories, e-mail and IP addresses, bearer/JWT/known tokens, `password=...` pairs, long mixed tokens), applied to bot text and engine lines before they are stored. It does not prove that nothing sensitive can appear (BIO-NFR-10).
- **Not changed:** the guard's own records still come from the runner log, which a bot can write to. The team in a record is taken from the writing process (CN-005), so a forged record can only blame its writer; its numbers are type-checked before they enter the log.
- **Still open:** the retry loop (BIO-306); where logs are stored (DB or object storage, DATA_MODEL); how long they are kept; whether Organizers should see staff diagnostics; an engine seed (`seed` is `null` in every log).

## CN-008 — Router turn checks, a host-side response deadline, hardened validator (2026-11-24)

- **Task:** self-review of `backend/match_runner` (`docs/SECURITY_REVIEW.md`, SR-01 to SR-06). Engineer's decisions under the owner's delegation (see CN-005).
- **Owner confirmation (2026-11-24):** the owner confirmed that these rules stay ("The rules stay"): the sender is charged for protocol violations and for a silent runner, and the router's response deadline stands. The deadline's numeric slack (2 s plus twice the limit) was not discussed and remains tied to the benchmark (DEC-04). Still reversible by a later change notice.
- **Defects found in my own earlier work and fixed** (each reproduced in a real sandboxed match first):
  - **SR-01 (High):** a bot could send engine calls during the other team's turn; the engine server read them as the other team's robot. Results could be manipulated (2 of 5 runs an A win in round 1, 2 of 5 a forfeit charged to the victim). The router now accepts a call only from the runner whose turn it is, and a null only as the answer to a notice it forwarded; a frame that breaks this is dropped and charged to the sender.
  - **SR-02 (Medium):** a bot could freeze its own process, and the in-process guard with it; the match then ended as a `platform_failure` after the whole-match timeout (a free replay). The router now has its own clock: a runner silent for more than `2 x max(turn, start-up limit) + 2 s` after being handed work is charged (`runner_unresponsive`).
  - **SR-03 (Medium):** an engine method number outside the engine's range crashed the Java server and was reported as a `platform_failure`. The router now refuses it and charges the sender.
  - **SR-04 (Medium, latent) and SR-05 (Low):** the validator reads only regular files (no symlinks, FIFOs, devices), at most 2 MiB, and reports unparseable or too-deep source as `E-SYNTAX`; team folder names must match `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`.
- **Behaviour changes:** new classification kinds under `bot_crash`: `protocol_violation` and `runner_unresponsive` (outcome `bot_failure`, the other team wins by forfeit, no rematch); public log wording per kind; `launcher.py` passes a deadline to the router whenever a limits profile is in force; validator results for hostile files change from a crash or hang to `E-FILES`, `E-SIZE` or `E-SYNTAX`; a normal match's `first_end` leg is no longer asserted by the tests (it is a race once `end_game` is sent; it never affected the result).
- **Trade-offs chosen on purpose:** the deadline slack (2 s plus twice the limit) is a guess and a heavily loaded host could charge a healthy runner; the 2 MiB validator ceiling is a safety limit for the validator itself, not the upload cap (`max_bytes` stays an owner decision); a frame with a valid method number and bad parameters is still attributed by which side closed the connection first.
- **Not fixed:** SR-06 (server-side Java exceptions are not counted as server errors) and the parameter-type residual in SR-03. A human or third-party review is still open.
- **Replaces:** nothing in the PRD. It makes CN-006's rule ("a bot cannot dodge a loss by breaking the match") true for three more ways of breaking it.

## CN-009 — Match jobs with platform retry and an Admin incident (2026-11-24)

- **Task:** BIO-306 and the core of BIO-301/302, in `backend/match_orchestrator/` (library only; no service, queue, API or database). Engineer's decisions under the owner's delegation (see CN-005); every item below is reversible by a later notice.
- **D1. Retry cap = 10 attempts in total** (the first plus nine retries), the DEC-05 recommendation. SRD-011 says "retry up to 10 times", which can also mean 11 attempts; the code takes `max_attempts` as a parameter (1 to 100). Only platform failures count; a bot failure ends the match.
- **D2. State after the cap is called `paused`** (DATA_MODEL left the name and the resume authority open). An incident `retry_cap_reached` is stored and the alert function is called. `resume_paused(match, actor, extra_attempts)` exists as a mechanism; **who may call it is not decided here**.
- **D3. A worker that disappears counts as a platform failure** (`worker_lost`) once its lease expires, and counts towards the cap, so a poison match cannot loop forever.
- **D4. A launcher answer is accepted only if it is consistent.** A winner without `ok: true` (non-zero exit, timeout) is retried instead of published, because the replay may be incomplete. Anything malformed is a platform failure; the platform never invents a winner.
- **D5. Configuration errors do not retry.** A missing bot folder or failed version check pauses the match at once (`configuration_error`). Port busy and host-lock timeout stay retryable.
- **D6. A match is played with the exact submission versions stored when it was created**; folders are `bots_dir/<submission reference>`, which an upload service must make immutable.
- **Behaviour change in `backend/match_runner`:** `launcher.PortBusyError` (a subclass of `LauncherError`) is raised for a busy loopback port; nothing else changed.
- **Not met, and why:** TC-04 requires "a new random seed" per retry. The engine's tie-break seed cannot be controlled (CN-005), so attempts record `seed: null` and a retry replays the same inputs. The orchestrator already passes a seed to the run function when one is supplied (`seed_fn`), so this needs only an engine-side change. The Admin alert has no real channel yet (notifications are a later epic): it is a function parameter, and an undelivered incident stays pending.
- **Still open:** DEC-11 (the JSON file store is a stand-in), BIO-303/304/305, who may resume a paused match, lease length versus match length (no heartbeat), and an independent review.
- **Replaces:** nothing in the PRD. It implements SRD-010/011, DATA_MODEL "Match" and the idempotency rule for worker jobs (API_CONTRACT section 8).

## CN-010 — Tie-break maps and the 50/50 coin flip (2026-11-24)

- **Task:** BIO-304 (PRD 6.4, SCN-03, TEST_PLAN TC-05), in `backend/match_orchestrator/tiebreak.py` (library only). Engineer's decisions under the owner's delegation (see CN-005); every item is reversible by a later notice.
- **Found in the engine source first:** the engine has no tie result. If points, robots alive and cheese are equal it calls an unseeded `Math.random()` inside the game and still names a winner, printing `The winning team won arbitrarily (coin flip).` (`battlecode.server.Server`, `DominationFactor.WON_BY_DUBIOUS_REASONS`). Its other tie-breakers (points, then robots alive, then cheese) are part of the game's own rules.
- **D1. A game is TIED when, and only when, the engine's reason line is that coin flip.** The engine's pick is stored (`engine_pick_ignored`) and never used. Games decided by points, robots alive, cheese, destroyed rat kings or resignation are decided. The line is an engine line that the launcher parses anchored (CN-007); bots cannot forge it. If the PRD means something else by "tie" (for example any game decided by a secondary tie-breaker), change `_absorb` only.
- **D2. A match is a series of games.** Game 0 is the scheduled map. If it is tied: normal stage = 1 predefined tie-break map, final = 3, played one after the other on the same teams and the same submission versions. The maps are fixed when the series is created. Each game is an ordinary match, so it has its own platform retry (cap per game), incident and exactly-once handling.
- **D3. Final stage: all three maps are always played** (PRD: "three maps automatically and sequentially"), even if two already decide it, so all three replays exist. The winner is the team with more tie-break map wins. A tie-break map that is tied again counts for nobody. Equal wins (including 0-0) go to the coin flip. The first game's result does not count once it is tied.
- **D4. A bot failure in any game ends the series at once** and the other team wins (`bot_forfeit`); remaining tie-break maps are not played (PRD: no rematch, opponent advances).
- **D5. The coin flip** is drawn once, by `secrets.randbelow(2)` (operating-system randomness), inside the same store transaction that records it, only when the series has no flip yet and is not finished. It is never redrawn: repeated jobs, second workers and restarts read the stored flip. A coin function that returns anything but `A` or `B` records nothing. The record (`id`, time, side, team, both tied teams, the games played, tie-break wins, `probability_each: 0.5`, `rerolls_allowed: false`) and the series `history` are the audit trail; `public_view` shows the flip without host paths, hashes or bot details.
- **D6. A game result needs the engine's reason line** to be accepted inside a series (otherwise the attempt is a platform failure, `missing_reason`, and is retried), because deciding "win or tie" without it would be a guess. Standalone matches are unchanged.
- **D7. Games of a series are never advanced on their own.** `take_advancement` returns nothing for them; `take_series_advancement` hands the series result to the bracket once.
- **Tested for real:** the example bot against itself on `DefaultSmall` ties by the engine's coin flip at round 1310 every time (symmetric position), so a real final-stage series plays four games and ends in one coin flip (3 of 3 probes, plus the integration test).
- **Not done:** where the tie-break maps are stored and chosen (TournamentMap, tournament setup), the qualification-cutoff draw (separate rule, needs the draw inputs, DEC-14), the screen and API that show the flip, the Admin audit log (the series `history` is only the source), who may resume a paused game, and the engine seed (TC-04). No independent review.
- **Replaces:** nothing in the PRD. It implements PRD 6.4 tie handling and SCN-03 on top of CN-009.

## CN-011 — Bracket, byes and the Organizer-started round runner (2026-11-24)

- **Task:** BIO-302 and BIO-303 without house bots, in `backend/match_orchestrator/bracket.py` (library only). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. The bracket is drawn once**, at creation, with the operating system's random source, and the draw (pairings, byes, time, method) is stored and never redrawn: creating the same bracket again returns the stored one. It is a fixed tree of size 2^k; later rounds pair the winners of neighbouring matches. PRD says "random pairings"; it does not say whether each round is redrawn. Redrawing every round is possible later without touching the rest.
- **D2. Byes:** `size - N` byes, all in round 1, each in a different pair, so no bye meets another bye and no later round has one. Which teams get them is random. A bye is recorded as already won (`result_type: bye`). Byes go to human teams (SRD-021).
- **D3. The last round is the final** (3 tie-break maps); every earlier round is normal (1 tie-break map). Each match is a series of CN-010. The play map of match `i` in round `r` is `play[(i + r - 1) % len(play)]`; where maps come from is a tournament-setup matter that does not exist yet.
- **D4. Organizer starts each round** (`start_round`, records the actor). A round can start only when the previous one is complete; starting twice changes nothing; `run_round` refuses an unstarted round. The matches of a round are played one after another.
- **D5. Advancement is read from the finished series and is idempotent** (`settle`). A match gets its winner once; the bracket marks the series' advancement as taken in the same transaction. A worker that dies between "series result recorded" and "winner advanced" loses nothing, which closes the gap CN-009 left open. Two workers on one round never play a match twice.
- **D6. A paused game pauses its round** (and keeps the next round locked) until an operator resumes the game and the round is run again. Who may resume is still undecided.
- **D7. House bots are refused with an error that names DEC-06.** The brief says only that they fill gaps and cannot advance or become champions; any algorithm for where they sit and what happens when one beats a human would be invented, and it would decide who can win. Implement it after the owner approves rules and examples (PRD: "needs approval and proof-of-concept testing").
- **Tested for real:** three example-bot teams play a 4-slot bracket with one bye to a champion (two series, each a coin-flip tie of four games). 23 tests in total, 22 unit and 1 real. Seven of eight deliberate breakages fail the suite; the eighth was an equivalent mutant (it kept byes in distinct pairs) and led to a test that bye places and pairings vary with the draw.
- **Not done:** house bots, the API and authorization for starting a round, a queue or service that runs `run_round`, storage of tournaments and maps, the qualification-cutoff draw, replay lifecycle, a champion/qualification hand-off, notifications. No independent review.
- **Replaces:** nothing in the PRD. It implements SRD-020, SRD-023 and part of SRD-021 on top of CN-009 and CN-010.

## CN-012 — Replay storage, access and purge at archive (2026-11-24)

- **Task:** BIO-305 in `backend/match_orchestrator/replays.py` (library only). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. Format = the engine's own `.bc26` file, one per game** (DEC-10 recommendation, still interim). A series of several games has several replays. Only the replay of the attempt that produced the recorded result is stored; replays of failed attempts are not. The file is checked on the way in: regular file, not a link, gzip magic and a complete gzip stream (a cut-off file is refused), SHA-256 equal to the one the launcher recorded. The size ceiling (512 MiB) is only a guard against a broken worker, not a product limit.
- **D2. Access rule** (PRD 6.4, API contract `GET /matches/{id}/replay`): Admin may see every tournament; an Organizer only assigned ones; a participant only tournaments where their team is registered, **any** match of that tournament, not only their own. The caller passes a `Viewer`; this module does not authenticate. No access and unknown game give the same `NotFound` (safe 404). After archive everyone with access gets `Gone` (410), **Admin and Organizer included**. A missing or damaged file gives `Unavailable` and a staff incident (FLOW-06). The stored hash is checked on every fetch.
- **D3. Archive = mark, then delete, then verify.** The tournament is marked archived first (from then on nothing is served and nothing new is stored: a worker that finishes late is refused, and the check and the file move happen under the same lock as the mark), then the folder is emptied and removed, then the records say `purged`. `replays_deleted` is `true` only after the folder is gone. A failed delete says `false`, raises a `purge_failed` incident and is retried by `purge_pending`; a crash between the steps is finished the same way. Every purge sweeps the whole folder again, so a file that reappears (restored backup, stray copy) is removed on the next run. A reader that already had the file open when the archive ran keeps reading until it closes it.
- **D4. Results, brackets, series and match records are not touched** by a purge (tested byte for byte on the match store). The index keeps who archived and when, the counts, and each replay's `deleted_at` and reason.
- **D5. Where files live:** `<vault>/<tournament>/<game>.bc26`, folders 0700 and files 0600, ids restricted to `[A-Za-z0-9._-]` with no `..`. A link in place of the tournament folder is never followed, for writes or for the purge. The index is a JSON file with the same lock and atomic-write rules as the match store (`JsonFileStore` gained two hooks for that); it is a stand-in for database tables (DEC-11), and the vault for private object storage.
- **Tested:** 39 tests (38 unit with real gzip files, 1 real engine match stored, served and purged), eight deliberate breakages (no access check, archived still served, late register allowed, unknown files not swept, purge claiming success on error, no hash check on fetch, no gzip completeness check, hash mismatch accepted) all fail the suite; one of them survived the first version, which led to a deterministic test of the register-versus-archive race.
- **Not done / not verified:** the HTTP endpoints, authentication and how a `Viewer` is built, notifications, backups of the vault, object storage and short-lived URLs, a browser player (DEC-10), whether a replay contains text a bot wrote (indicator strings, which the engine can put in replays) and so whether showing every replay to every participant leaks anything the owner cares about, space limits, retention if an archive is never run, and who may archive (the API says Admin or assigned Organizer). No independent review.
- **Replaces:** nothing in the PRD. It implements SRD-070 and the storage, access and purge parts of BIO-REQ-08 (TC-08 steps 1, 2, 4, 5 at library level).

## CN-013 — Upload check: static check and a trial match (2026-11-24)

- **Task:** BIO-202 (PRD BIO-REQ-04 "runtime compatibility before activation", SRD-050/051), in `backend/submission_check/` (library only). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. Runtime validity = a trial match.** After the static check passes, the exact validated bytes play two full games on `DefaultSmall` against the scaffold's example bot (pinned by SHA-256): the candidate on side A, then on side B. Both sides, because a bot can fail only on one side's start positions. Winning is not required.
- **D2. Three outcomes.** `valid`; `rejected` (static error, or the candidate crashed, hung, broke the protocol or breached a limit: participant must change something); `inconclusive` (platform failure, busy host, or the *reference* bot failed: nobody is blamed, the file does not become active, it is checked again). A participant fault outranks an inconclusive game.
- **D3. The verdict is bound to the file.** The file is read once; what was validated is what is staged, played and hashed. `may_activate(verdict, sha256)` is true only for `valid` with no reasons and that exact hash, so a file swapped after the check cannot ride on an old verdict.
- **D4. Reasons are fixed wording.** Bot-written text never becomes a reason; the bot's own output is attached separately as the participant view of the structured log (redacted, clipped).
- **D5. Same host lock as tournament matches** (one engine port per host); the trial uses the sandbox and the same limits profile, so what is rejected follows the interim limits (DEC-04).
- **Tested:** 21 tests (19 unit, 2 real games); ten deliberate breakages, eight caught at once and two (re-read of the file; static re-check of the read bytes) caught after two tests for a swap between validation and staging were added.
- **Not done:** upload endpoint, storage and activation state, history of verdicts (SRD-053), upload size limit (DEC unset), throttling and queueing of checks, which maps and how many trial games, independent review.
- **Replaces:** nothing in the PRD. It implements the "runtime" part of BIO-REQ-04 and the gate behind SRD-051.

## CN-014 — Map pools for tie-breaks (2026-11-24)

- **Task:** BIO-303/304 follow-up in `backend/match_orchestrator/maps.py` (library only). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. Engine maps only.** A pool may use only maps shipped in the pinned engine jar (43 in 1.2.6). Organizer-uploaded maps are hostile input (size, format, validation not designed) and are not supported.
- **D2. A pool is one immutable version.** Played maps (1 to 50), 1 tie-break map (normal tie), 3 tie-break maps (final tie), the engine version and each map file's SHA-256. A different set is a new pool id; the same content again returns the stored pool; different content under one id is a conflict (DATA_MODEL: map references are immutable by version, SRD-012).
- **D3. A tie-break map must not also be a played map; maps within a list do not repeat.** The PRD says "predefined tie-breaker map(s)" without saying more; a tie "broken" on a map the teams already played is not a new test. The normal and the final tie-break lists may share a map. Reading is mine; the owner may relax it.
- **D4. A bracket is drawn only on a pool that matches the running engine** (`create_bracket_from_pool`): a missing map, a changed file or another engine version refuses the draw. The pool id is stored on the bracket, and a second pool id for the same bracket conflicts. The check runs at draw time only, not before each round.
- **Tested:** 34 tests (32 unit with a built jar, 1 on the real pinned jar, 1 real two-team final on three real tie-break maps with `BIO_INTEGRATION=1`); twelve deliberate breakages: eleven caught, one equivalent (the declared-size check, the bounded read behind it catches the same file). One survivor became a test (a second pool with identical maps). All pass on Python 3.12 to 3.15.
- **Not done:** custom maps, who chooses a pool and where tournament settings are stored (EPIC-04), re-verification before each round, the map list shown to participants, no independent review.
- **Replaces:** nothing in the PRD. It supplies the "predefined tie-breaker maps" that SRD-024/025 and CN-010 assumed.

## CN-015 — Whole-tournament simulation on the real engine (2026-11-24)

- **Task:** `backend/match_orchestrator/tests/test_tournament_e2e.py` (test only, no product code changed). It plays the pieces built so far together: a map pool from the real engine jar, a drawn bracket for **five** human teams (so byes), rounds started one by one, real sandboxed matches, replays collected after each round, then archive.
- **What it checks:** the crashing team loses its first real match by `bot_forfeit` in a single game and never wins; the example bot against itself ties game 0 (the engine's own coin flip), so every normal match plays the one pool tie-break map and the final plays all three in order; a stored platform coin flip exists exactly when `result_type` says `coin_flip`, with no rerolls; every winner is advanced once (`advancement.taken_at` set) and a second worker re-running every round changes nothing; no alert is raised; replays are stored for finished games, a participant of the tournament can fetch one, a stranger gets `NotFound`, the files are on disk before the archive and gone after it, `Gone` for Admin, and the bracket and champion are untouched.
- **Result:** it passed on the first real run (about 48 s); it found no defect, so no code was changed. Four deliberate breakages (pool tie-break map ignored, advancement never taken, collect stores nothing, archive reports a purge without deleting) were each caught; the last one survived the first version of the test (a `Gone` answer does not prove the files were deleted) and the test now checks the folder on disk.
- **Not covered, so TC-05 is still open:** house-bot fillers (DEC-06), the qualification-cutoff draw (DEC-14), a tournament with more than five teams, API and authorization, a queue or service between the Organizer's click and the worker, Admin alert delivery, a bot-forced platform failure inside a tournament. Only the example bot and one crashing bot were played, so nothing here says the bracket is fair for stronger or stranger bots.


## CN-016 — Submission registry: versions, activation, history, deadline lock, access (2026-11-24)

- **Task:** BIO-EPIC-05 (follows BIO-202; PRD BIO-REQ-14, SRD-050 to SRD-058), `backend/submission_registry/` (library only: no endpoint, no authentication, no tournament storage). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. Who may do what (DEC-02 recommendation, adopted):** only the **captain** of a team uploads; every team member reads history and downloads; the assigned Organizer and Admin read and download but every write is refused (`Forbidden`). Admin does not upload on a team's behalf. Anybody else gets `NotFound`, the same answer as for a team that does not exist.
- **D2. Two stages.** `submit` runs the static check on the exact bytes at once (SRD-050) and stores every upload as an immutable version, `validating` or `invalid` with the reasons (invalid versions stay in the history and use a version number). The trial match (`submission_check`) is run by a worker: `claim_check` (one worker at a time, a lease of 30 minutes, then a dead worker's claim can be taken over), then `record_verdict`; `run_check` does both and gives the claim back if the check itself cannot run. A verdict is accepted only for the live claim and only if it names the exact stored file.
- **D3. Activation (SRD-051/052).** `valid` -> the highest valid version is active. `rejected` -> `invalid`; `inconclusive` -> may be checked again; neither displaces the active version. A late verdict for an older version does not replace a newer active one.
- **D4. Deadline (SRD-054).** The upload time counts: an upload before the deadline may still be checked and activated after it; a refused upload uses no version number. The registry does not store deadlines: the caller passes the current one, so an Admin extension is just a later deadline. A retry of an upload that already succeeded returns the same answer even after the deadline (idempotency key per team; the same key with other bytes is a conflict).
- **D5. Storage and immutability (SRD-055).** `<root>/<team>-v<N>/bot.py`, folder 0500 and file 0400, so `<root>` can be the match runner's `bots_dir` as it is. Before any worker, download or match uses a version, the folder is checked again (plain folder, only `bot.py`, SHA-256 equal); a mismatch is `Unavailable` plus a staff incident. `pin_tournament` records, once and after the deadline, which version each team plays with (write-once; refused while a team still has an unfinished check unless the caller allows it); `verify_pins` re-checks the pinned folders before a round.
- **D6. Interim limits, not product decisions:** 256 KiB per file, 500 versions per team (history is kept, so uploads must be bounded).
- **D7. Staff reads are audited.** A download by an Organizer or Admin writes an audit entry; team members' own reads do not.
- **D8. The bot's own output is not stored.** The trial verdict can carry the bot's redacted output (CN-013); the registry keeps only fixed-wording reasons, the per-game judgement and numbers, clipped. Showing the participant that output needs a separate decision.
- **Tested:** 55 unit tests (fake clock, hand-made verdicts, parallel uploads, tampered, replaced and orphaned folders) and 2 real ones with `BIO_INTEGRATION=1` (an example bot uploaded twice, really checked, activated, pinned and played through the match runner from the registry folders; a real crashing bot rejected while the active version stays). Passes on Python 3.12 to 3.15. 24 deliberate breakages: 23 caught at once; the survivor (verdict about another file for a non-valid status) became a test and is caught.
- **Not done:** upload endpoint and error format, authentication and how an `Actor` is built from a session, tournament and deadline storage, deadline extension and emergency override, registration link (is this person on this team in this tournament), notifications, rate limiting beyond the version cap, deletion and retention of source files (DEC-13), the database (DEC-11), calling `verify_pins` from the orchestrator, a queue that feeds `run_check`, no independent review.
- **Replaces:** nothing in the PRD. It implements the state and rules around `bot_validator` and `submission_check`.


## CN-017 — Worker and job queue outside the web process (2026-11-24)

- **Task:** BIO-EPIC-03 (SRD-007, BIO-REQ-05), `backend/work_queue/` (library plus a command-line worker; no API, no scheduler). Engineer's decisions under the owner's delegation (see CN-005); each is reversible by a later notice.
- **D1. Two job kinds, ids only.** `check_submission` (the CN-013 trial match through `submission_registry.run_check`) and `run_round` (`bracket.run_round`). A payload that carries anything else, a path or a different key, is refused, so a job cannot name code or a file. The queue is a JSON file with the same lock, atomic write and "damaged is never empty" rules as the match store; it is a stand-in until DEC-11.
- **D2. One live job per key; claim, lease and renewal.** Enqueueing the same work returns the live job. A claim has a token and a lease (120 s default) that a helper thread renews while the handler runs. A lost lease is taken over and counts as a failure of the job. An outcome from a worker that lost the claim is refused.
- **D3. Retry policy (interim numbers):** 5 failures (errors or lost leases) then `dead` with an incident and an alert; waits of 30 s doubling to 1 h. `Permanent` is dead at once. A deferral (someone else holds the work) is no failure but ends dead after 1000.
- **D4. An inconclusive upload check is a job failure, not a result.** The version stays not active, the participant is not blamed (CN-013 D2), the check is retried by the queue; at the cap staff get an incident. A rejected bot is a normal, finished job.
- **D5. A paused round finishes its job.** The orchestrator already holds the incident; an operator resumes the game and queues the round again. Who may resume is still open (CN-009).
- **D6. Shutdown.** First SIGTERM/SIGINT finishes the running job and stops; the second hands the job back without a failure.
- **D7. One engine match per host.** The worker passes the same `host.lock` to trial games and tournament games; the registry folder is the match runner's bots dir.
- **Tested:** 53 tests (52 unit, 1 real: the worker started as a separate process checks two uploaded example bots, then plays a started final round with real sandboxed games, 44 s; `BIO_INTEGRATION=1`). Unit tests pass on Python 3.12, 3.13, 3.14 and 3.15. 29 deliberate breakages (rule by rule: stealing live jobs, token not checked, no dedupe, no cap, no renewal, signal counted as failure, inconclusive treated as done, host lock not shared and others) were each caught; the last one needed a wiring test that the first version lacked.
- **Not done:** an API or scheduler that enqueues work (nothing yet queues a check at upload time, calls `purge_pending` or `verify_pins`, or sends notifications), several hosts, a worker container or image, a real Admin alert channel, renewal of the orchestrator's own per-attempt lease (2400 s), the database (DEC-11), independent review.
- **Replaces:** nothing in the PRD. It supplies the worker boundary that SRD-007 and the architecture's ADR-03 ask for.
